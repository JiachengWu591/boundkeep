## 3. 取舍

- **R42-1 为什么另记、还要有上限，不干脆不算**：不算进任何时钟，每次问盘都要几毫秒的盘上，一次遍历的工作线程就可能卡几十秒（次数受条目数限制，最多 30000 次）；守护进程 2 秒就放弃、回答问，但线程还在跑，卡住的线程多了，所有调用都是"忙"的问。有上限，线程最多多跑 1.5 秒。
- **R42-1 的上限为什么是 1.5 秒，不是这份预算的 0.35 秒**：第一版定的是 0.35 秒（"一次遍历最多多花一份预算的时间"）。量的时候 R40-1 的布局问兄弟要 0.25 到 0.28 秒，记成了代价"盘再慢两成多就到上限"。跑验证链时就到了：修订 42 复审的探针（`rv43_probe42.py`）里 B1（27000 个没有兄弟的带点空目录）四条（`rg made .`、`tar -czf ../o.tgz .`、`Copy-Item -Recurse . ..\b`、`Grep path=.`）都是 `recursive-scan-budget`，由拒绝变成问，每次判决 0.93 到 0.99 秒（单独跑时 0.81 到 0.83 秒）。之后加了跟踪单独重跑这个探针：问兄弟 0.25 到 0.31 秒，遍历自己 0.14 到 0.19 秒，所以到的是问兄弟的上限，不是遍历的。这正是 R42-1 要修的那一类（问兄弟让拒绝变成问），只是门槛从 0.35 秒的遍历时钟挪到了 0.35 秒的另一份。次数本来就受条目数限制：一份预算最多 30000 个条目，这台机器上每次约 10 微秒，全问也只要 0.3 秒；1.5 秒是它的五倍，低于守护进程的 2 秒。到了 1.5 秒的请求，没有后端时守护进程本来也等不到它走完。
- **R42-1 为什么不只对含 `~` 或非 ASCII 的名字问盘**：复审说过，挡不住把目录起名叫 `k~0001.` 的布局；文件兄弟那一半（成对的布局）靠列表记文件就省掉了。
- **R42-2 为什么第一个照旧留着**：每个 `cd` 都可能失败（`;` 连着时后面照样跑），这一行开始时的目录是那时的工作目录；原有测试 `test_the_set_of_possible_directories_is_bounded` 也要求它在。这次的目标排在其他旧目录前面：几个 `cd` 都成功时，真实的工作目录就在里面。
- **R42-2 为什么丢掉了目录就不送审**：第一版只照复审的建议换了留哪几个。跑完验证链之后，照复审自己的教训（"有上限的列表要看丢掉的是哪一个"）把方向反过来量（`rv43_cdorder.py`，项目外 `o/.kube/config`，9 种写法，新旧代码比）：先 `cd <外面>/.kube`、再接三个会失败的相对 `cd`，`.kube` 既不是第一个、也不是这次的目标，被丢掉；`cd <K>; cd q; cd r; cd s; cat config`、同样的 `&&` 写法、四个 `cd`、`cd q; cd <K>; cd r; cd s; …`、PowerShell 的 `Set-Location` 写法，修订 42 拒绝，第一版送审。上限是几都一样：多写几个会失败的 `cd`，总能把要紧的那个挤出去。所以照"看不全就不送审"：丢掉了目录，这一行直接问、不送审；留哪几个仍照上一条，在留下的目录里找得到时照样拒绝（修订 42 送审的 `cd q; cd r; cd s; cd <K>; cat config` 现在拒绝）。也想过同时留修订 42 的前 7 个和这次的目标（最多 14 个），把 `.kube` 放在中间照样挤得出去，没有采用。不改 `MAX_CWDS`：上限本来就是为了不让每个相对路径在 2 的 n 次方个目录里各解析一次。
- **R42-4 为什么两种都查**：复审的建议。量下来，假目录 `VAULTS~1.` 是普通目录时，R42-5 那处改动（写法那份不能往下找时也加一份）已经让它按 key 走到 `vaultstorage.`；假目录是联接、指向别处时，只有查 key 那一次走得到（补了一条测试，变异 `both43:first-only` 只由它抓到）。每条路径最多多一次查询。
- **R42-5 为什么另加一份路径，不改 `resolve_on_disk`**：`resolve_on_disk` 程序名也用，改它会让程序路径里带 `~数字` 长名的程序由灰色变成认得出，超出这次的范围。另加的那份只在写法里有像短名的名字、盘上又确实是长名时出现；写法那份照旧不确定，放行那边看到的和原来一样（有测试）。
- **R42-5 为什么通配符匹配也要，是怎么发现的**：变异整批里 `scan42:unwalkable-kept-dropped`（"不能往下找的路径，它记下的盘上地方不走"）存活，修订 42 是抓到的。修订 42 里抓到它的是 `notes~1.` 那条测试；修订 43 给那种写法另加了一份能往下找的路径，那条测试不再经过这段代码。去找还有谁经过它，搭了探针（`rv43_globlong_probe.py`）：
    - 通配符匹配到 `data~1` 下面带点的目录（`rg made data~1/k*`、`rg made data~1/*`、`Copy-Item -Recurse data~1/k* b`，盘上是 `data~1/k9./.env`）还要靠这段代码，去掉它就由拒绝变成送审，没有测试。补了一条测试，变异只由它抓到。
    - 通配符匹配到 `data~1` 本身或它下面不带点的名字（`rg made *`、`rg made d*`、`rg made data~1/*`、`tar -czf o.tgz d*`、`Copy-Item -Recurse data~1/* b`，盘上是 `data~1/sub/.env`），修订 42 和第一版修订 43 都送审：匹配那份和写法那份一样不确定、不往下找，第一版只给写法加了长名那份。这是 R42-5 的同一个问题换了个写法，所以照 R42-5 修（先改规格）：匹配到的名字也查一次盘，是长名就多一份确定的路径。
    - 带 `glob-match`：展开了变量才找到的匹配不进请求（修订 38，R37-1），长名那份也得跟着不进；变异 `glob43:long-no-reasons` 去掉它，请求里就多出展开后的目录（有测试）。不带变量时，送审的请求里它和写法的长名那份一样，同一个文字出现两次。
    - 也看了 `cd d* && rg made sub`：照旧送审，`cwd-unknown`；换成普通的名字 `dir1` 也一样，修订 42 也一样，是 `cd` 进通配符时工作目录不知道的老规则，不属于 R42-5。
- **R42-6 为什么只对 key 查到的**：Win32 程序只能经短名进到名字以点结尾的目录（直接写 `archivefolder.` 时 Win32 去掉点，打不开它）；经保留点的原文到达的，是 Git Bash 那类保留点的程序，在里面也保留点。
- **R42-3 不改代码**：使用者定的范围是复审的推荐，复审推荐只写进规格。
