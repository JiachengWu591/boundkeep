## 4. 与计划的偏差

计划的 D1 到 D8 都照做了。下面是做的过程中发现、改了规格再改代码的地方，都已写进修订 44：

1. **已有测试的 `expect` 会被改写（D1 的例外）。** 基准第一次运行，"禁止 curl"这类收紧规则被整份拒绝：默认策略里有几百条 `expect: gray` 的测试，用来防止规则过宽，收紧之后它们就"失败"了。现在的做法：已有测试的判决因新规则变严、两台假机器一致时，改写它的 `expect`，列在输出里，并给出警告 `existing-tests-changed`；变松（灰色变成 allow）照旧拒绝。
2. **新测试的 `expect` 按实际写入。** 提议者只看得到规则 id，猜不准一条测试在已有规则下的判决。所以判决不由新规则决定的新测试，按实际判决写入（注明 `test-expect`），两台机器不同就拆成两条。由新规则决定的，必须与 `expect` 相同。
3. **加入提议之前就失败的已有测试只注明**，不拒绝（`tests-already-failing`）。
4. **每个 `boundkeep policy` 子命令都在代码里拒绝 Claude Code 的进程**（自查发现）。2026-11-26 之前安装的策略文件没有那条拒绝规则，agent 本来可以运行 `policy add --dry-run`（花你的钱）或 `policy check`（打印审计日志）。这一道检查可以靠清掉环境变量绕过，所以策略里的规则仍然要有。
5. **提示词列出会报子命令的程序。** 基准发现 `terraform apply`、`kubectl delete`、`make lint`、`twine upload`，以及 Bash 里的 `reg add`，在规则语言里没有子命令，这样写的规则永远命中不到。检查以 `tests-few` 拒绝它们是对的。提示词现在列出了名单；有测试核对名单上的每个程序确实报子命令，PowerShell 的 `sc` 要写成 `sc.exe`（`sc` 在 PowerShell 里是 `Set-Content`）。
6. **dev 回放只取标签已确认的样本**，与评测报告的口径一致。
7. 多了 `boundkeep policy history`（列写入与撤销的记录），写进了规格。基准不做回放：dev 切分对每个用例都一样，而且要源码仓库。
8. 审查之后（第 6a 节），allow 规则的检查改成问归一化层（`ProgramProbe`）；allow 规则的路径必须限定在项目里；联网必须有 `domain_in`。

## 6. 已知问题与局限

1. **在线模式没有接过真实服务。** 真实模型能不能按提示词写出可用的提议、写得多宽，都没有测量。基准的真实后端模式由你运行。
2. **金丝雀是有限的名单。** 很窄的 allow（只放行 `~/dev/shared/**` 的读）碰不到它们。放宽方向的安全靠三件事：只能新增、最严者胜、allow 规则的语法限制；属性测试只覆盖其中"新增不削弱 deny/ask"这一条。
3. **审计日志的回放是近似。** 只回放 shell 调用；用 `cwd` 当项目目录；按新会话判；被截短的命令不回放，脱敏改写过的按改写后的文本判。
4. **"没有子命令的程序"只能对整个程序写规则。** 这是规则语言的限制，M4 不改它。
5. **改写已有测试的 `expect` 是新增之外唯一会动原有内容的地方。** 它只朝变严的方向改，而且要两台机器一致。改写的条数多时，可能是规则过宽，只给警告，不拒绝。
6. **用户已经安装的策略文件**不会自动得到 `policy` 这个子命令。代码里的检查挡得住没清掉环境变量的 agent，挡不住清掉的。`docs/policy-nl.md` 写了怎么更新。
