# M1c-3 验收报告：`allow-cd-family`

里程碑：给改工作目录的命令加一条 allow 规则（仅 default）。日期：2026-10-21。实现者没有提交、没有推送，没有碰 `src/`、`~/.boundkeep`、`~/.claude`，没有执行任何被测命令（只做归一化）。

## 1. 结论

**加了一条 `allow-cd-family`（default 现为 68 条规则，strict 仍是 53 条，唯一的 allow 仍是 `read-inside-project`）。它与任务书有两处不同，都是为了不比今天更宽松，需要你确认（第 2 节）：规则带 `path_inside_project`（不是"没有路径条件"），并且不含 `popd` / `Pop-Location`。** 真实会话里最常见的形式（`Set-Location 'E:\proj'; <allow 命令>`、`cd src && ls`）整行变成 allow；`emit_allow` 仍是 `false`，allow 只是"无决定"。

## 2. 与任务书不同的两点（有证据）

1. **规则必须要求目标已知在项目内（`path_inside_project: true`）。** 我把"没有路径条件"的版本放进临时策略（只在 scratchpad，没有进仓库）对比过，两个问题都是实测：
   - **`cd ../other && git status` 变成 allow，而 `git -C ../other status` 是 ask**（`ask-git-read-outside-project`）。`git status`、`pwd`、`Get-Location`、`Get-Date` 不带路径，它们的目录来自前面的 cd，没有任何路径供规则判断，所以"之后的每个命令按新目录判定"只对带路径的命令成立。`cd /tmp && git status`、`cd ~ && git status`、`cd ../other && git log`、`cd ../other && git diff` 同样从 gray 变 allow。
   - **动态目标变成 allow：`cd $x`、`cd "$(pwd)"`、`Set-Location $x` 单独成行是 allow，`cd $x && git status`、`cd - && git status`、`cd ~ && git status` 整行 allow。** 原因：这些 cd 的 Action 不是灰色（`gray=False`，`gray_reasons=()`），只是路径的 `inside_project` 为 `None`；今天它们是 gray 仅仅是因为没有 allow 规则可匹配。"匹配器不让 allow 匹配灰色动作"在这里帮不上忙。要靠规则本身排除，规则语言里"路径已知"的唯一表达就是 `path_inside_project`。
   - 代价很小：项目内的 cd（`Set-Location 'E:\proj'`、`cd src`）覆盖了任务书要解决的主要场景；项目外的 cd 要放行必须先改归一化层（让动态目标的 cd 带灰色原因）并想清楚无路径命令的问题，这超出本轮（不得改 `src/`）。
2. **`popd` / `Pop-Location` 以及不带路径的形式（光秃秃的 `cd`、`pushd`、`Set-Location`、`cd -`）不在规则里。** 它们没有路径，`path_inside_project` 要求至少一条路径，所以不匹配，今天是 gray，仍是 gray；规则语言不能表达"没有路径，或路径在项目内"。把它们列进 `program` 只会让规则含有永远匹配不到的名字，所以没有列。因此任务书语料例子里的 `pushd src; popd` 是 gray（语料里标 keep-ask），`pushd src && ls` 是 allow。

## 4. 规则文本

```yaml
  - id: allow-cd-family
    tool: [Bash, PowerShell]
    match:
      program: [cd, pushd, Set-Location, Push-Location]
      paths_read_only: true
      path_inside_project: true
    action: allow
```

（完整注释在 `policies/default.yaml`；放在 `allow-ps-data-shaping` 之后、`allow-devtools-trusted-project` 之前。）`sl`、`chdir`、`cd`（PowerShell）、`pushd`（PowerShell）由归一化层统一成 `set-location` / `push-location`，所以四个名字覆盖全部写法；PowerShell 动作的程序名比较不分大小写。

## 5. cd 目标由哪条规则判定

| 目标 | 判定者 |
|---|---|
| 项目内且已知（`src`、`.`、`./`、`src/..`、项目根的绝对路径、`~/proj/src`） | `allow-cd-family`（allow） |
| `~/.ssh`、`~/.aws`、`.env`（cd 携带的目录路径是 read） | `no-secret-read` / `no-credential-store-read`（deny）；allow 规则对 `cd .env` 也命中，但 deny 最严者胜 |
| `\\server\share` | `net-allowlist`（ask） |
| 项目外（`..`、`/tmp`、`~`、`~/.claude`、`C:\`、兄弟目录 `proj-evil`、POSIX 大小写变体 `PROJ`） | 没有规则 → gray（和今天一样） |
| 动态（`$x`、`$(...)`、通配符、`cd -`、光秃秃的 `cd`、`popd`、提供程序路径） | 没有规则 → gray（和今天一样） |
| 项目内的 `.git`、`.claude`、`certs`、`secrets` 目录本身 | 没有规则保护目录（只保护里面的文件）→ cd 是 allow；**之后的命令按新目录判定**：`cd .git && cat config` deny（`no-credential-store-read`），`cd .claude && cat settings.local.json` deny（`no-agent-state-read`） |
| cd 之后的命令 | 按新目录判定：`cd .. && cat .env` deny、`cd src && cat ../.env` deny、`cd /etc && cat shadow` POSIX deny / Windows gray；`cd` 可能失败，所以旧目录与新目录同时保持可能（`cd src && cat ../README.md` 从项目根看 `..` 在项目外，gray） |

## 8. 没放行的、以及残余风险

没放行：项目外的 cd、动态目标、`cd -`、光秃秃的 `cd`、`popd` / `Pop-Location`、不带参数的 `pushd`、`chdir`（Bash，不是内建）、`if` / `foreach` / `try` 里的 cd、带包装器与重定向的 cd、`cd` 之后任何本来就不是 allow 的命令（`pip install`、`python script.py`、`rm`、`Set-Content`、`pytest`（untrusted）……）。原因见第 2 节。

**残余风险 / 已知缺口（请你决定要不要在归一化层补）：**

1. **Bash 的 `cd a b`（两个参数）仍可能是 allow**（实测：`cd src x && git status` 在两台机器上都是 allow，今天是 gray）。归一化层只把第一个词记成路径，`x` 不可见。在 bash 里这是 `too many arguments` 错误，但在 zsh（macOS 默认 shell）里 `cd old new` 把当前目录里的 `old` 换成 `new`，可能落在项目外，之后不带路径的命令（`git status`、`pwd`）在那里运行。建议改 `src/boundkeep/normalize/programs.py` 的 `_h_cd`：多于一个位置参数时给 `cd` 加灰色原因（例如 `cd-extra-arguments`），或者把所有位置词都列成路径。**这需要改 `src/`，我没有改；没有写测试把这个缺口固定为"正确"，也没有把它放进 `adv` 语料（因为它现在是 allow）。**
2. **`cd` 可能失败，旧目录与新目录同时保持可能。** 保守方向，所以 `cd src && cat ../README.md` 是 gray（从项目根看 `..` 在项目外），`Set-Location src; Get-Content ..\README.md` 同样。多级的 `cd a && cd b && cd c && ...` 超过 `MAX_CWDS` 后变未知目录，相对路径变不确定，整行 gray。
3. **`pipeline` 头的 `cwd` 追踪**：`'src' | Set-Location` 的 cd 动作有路径（管道头），但 `_after_cd` 看不到管道头，把新目录记成主目录（保守）。我推理了这个差异不会放宽（旧目录始终在追踪列表里，且项目根是最浅的项目内目录），没有单独的测试覆盖。
4. 项目里指向项目外的符号链接 / 联接点：与其他 allow 规则同一套磁盘解析逻辑（`scan_disk`），假机器上不扫盘，所以没有测试覆盖。
5. 这条规则让 `Set-Location 'proj'; <allow 命令>` 在 boundkeep 这一层不再多问；`emit_allow` 仍是 `false`，allow 之后 Claude Code 自己的权限流程（包括它自己对项目外 cd 的确认）照常决定。
