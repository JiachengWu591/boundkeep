# M1c-2 验收报告

里程碑：开发工具预设（挂在 `trusted_projects` 后面）、数据整理 cmdlet、PowerShell 管道开头的修复。日期：2026-10-20（测试与度量由主会话在 2026-10-20 到 21 运行，见各节的标注）。

## 1. 结论

**自动验收、Linux 容器验证和真实 Claude Code 冒烟都通过（Linux 完整套件在最后一处测试修改之后没有重跑，见第 9 节）；手工验收（`docs/manual-acceptance-m1c2.md`）、对新增面的定向 X1 审查、以及在你自己真实会话上用 `--trust` 测量覆盖率，都还没做。等你对第 8 节做选择，并完成第 9 节的前置条件。**

需要当面说清的五件事：

1. **这个预设默认完全不生效。** `trusted_projects` 缺省是空列表，所以不改任何设置的用户，`pytest`、`ruff` 等仍是灰色（ask）。只有你在自己的终端里运行 `boundkeep trust add` 之后，那个项目里的开发工具命令才在规则层被判为 `allow`。**strict 永远不放行**（strict 没有这些 allow 规则）。
2. **`allow` 仍然是"无决定"。** `defaults.emit_allow` 仍是 `false`：规则判 `allow` 时 boundkeep 输出"无决定"，Claude Code 自己的权限流程要不要弹框，由 Claude Code 决定，不由 boundkeep 决定。本里程碑只让 boundkeep 在你明确信任的项目里不再多问一次，不替你批准任何东西。
3. **信任一个项目，就是让它自己的代码不经审查地运行。** 与"项目内写入"的 allow 规则合起来，这形成"先写后运行"的链路：被提示注入的 agent 可以先用 `Write` 写 `tests/test_x.py`（普通项目文件，放行），下一次调用再运行 `pytest`（在受信任项目里放行），这两步各自都是 allow，**没有任何规则能看到"上一次调用写了什么"**。只应信任你自己写的或审计过的仓库。
4. **度量用的语料是合成的。** 第 6 节的"每百动作问询数"说的是设计语料（`tests/corpus/workflow_benign.yaml`），不是你的真实会话。真实效果要用 `scripts/session_command_stats.py --trust <你的仓库>` 测，你**还没有运行**，所以**未验证**。
5. **规则层的天花板很低，这个里程碑不改变它。** 见下一节：对 PowerShell 脚本味很浓的工作流，规则层最多放行约 20% 到 30%，其余要靠 M3 的 LLM 层或用户确认。

## 2. 为什么做

这是 M1c 之后的数据驱动补强。主会话用 `scripts/session_command_stats.py` 在你自己的会话记录上跑了一次（60 天，开发 boundkeep 本身，PowerShell 为主）。下面是聚合输出的要点，是主会话记录的结果，**我没有重跑**，脚本只输出聚合，不含命令、路径或项目名：

- **PowerShell 工具 3354 次调用，只有 1.1% 被 M1c 的规则放行。**
- 挡住它们的原因，按量排序：
  - `program-path-qualified` 约 1300 次：几乎全是项目自己的 `.venv\Scripts\python.exe`、`ruff`、`mypy`（路径限定的程序一律灰色）。
  - `ps-compound`：赋值 1730、`if` 250、`foreach` 181 等（复合语句）。
  - `ps-dynamic`：成员访问 768、方法调用 674、二元表达式 666、脚本块约 570、类型表达式 486。
  - `exec-of-written-file` 399 次。
- `Edit` / `Write` 被拒绝的主要是 `protect-guard-code`：编辑 boundkeep 自己的源码。这是开发 boundkeep 才有的现象，不是普通用户的负担。

规格（修订 5，§1 前置条件与 §7 新增的"开发工具预设与受信任项目"一段）据此记录了结论：**规则层无法把一个 PowerShell 脚本味很浓的工作流提到约 20% 到 30% 以上的放行率；其余需要 M3 的 LLM 层或用户。** 所以 M1c-2 只做规则层能安全做的两件事：（一）会运行仓库代码的开发工具，只对用户明确信任的项目放行；（二）几个只整理管道内容的 PowerShell cmdlet，加上让它们安全所必需的管道开头修复。

## 3. 交付物

字段与规则的完整说明在 `docs/policy-reference.md`（实现者已更新，含"受信任的项目"和"Dev-tools preset (trusted projects)"两节与规则行），PowerShell 一侧的说明在 `docs/powershell-dialect.md`（已更新），设计决定在 `PROJECT_SPEC.md` §7 新增的"开发工具预设与受信任项目"一段与修订 5。本报告不重复，只列要点（我对照仓库逐条核对过）。

**(a) 策略语言：`trusted_projects` 与 `project_trusted`**

- 顶层键 `trusted_projects`（默认空；`policies/default.yaml` 里没有这个键，是 `trust add` 在 `version:` 之后创建它）；匹配字段 `project_trusted: true`；`Action.project` 与 `Action.project_resolved`（`normalize/event.py` 的 `_project_keys`）。
- 项目是否受信任，对链接敏感：`project_resolved`（符号链接 / junction 解析后）与 `project` **两者都**要在受信任的项目里才匹配。会话的 `cwd` 在项目之外时 `Action.project` 为 `None`（命令不是在运行这个项目的代码），不匹配。
- 加载器（`policy/schema.py`）拒绝：相对路径、UNC、含通配符或变量的条目、`..`、`~user`、NTFS 备用数据流、翻译过的 `/mnt/c` 形式，以及过宽的目录（主目录及其祖先、盘符根、`/`、`C:\Users`、`/tmp`、系统目录、主目录下的 Documents / Desktop / Downloads 本身等）。最多 64 项。**`too_broad` 与归一化层拒绝过宽项目根是同一份代码**（`policy.schema.too_broad`，`event.py` 里的 `_too_broad` 只是它的别名）。
- 单独写 `project_trusted` 不满足"allow 规则必须点名工具或程序"的加载检查。

**(b) `boundkeep trust add|remove|list`（新增 `src/boundkeep/trust.py`）**

- **文本编辑**：只改 `trusted_projects` 那一块，注释、键的顺序、换行符与 BOM 逐字节保留；编辑前后用 YAML 比较，确认除这一块之外没有变化。
- **先验证再写**：编辑后的文本先用真正的策略加载器（`parse_policy_text`）验证，再原子地、私有权限地写回（`_atomic_write` + `ensure_private_file`）。被拒的编辑（过宽的目录、不能加载的策略、不寻常的写法）不碰文件。
- **`add` 在 stdin 不是真正的控制台时拒绝**：Windows 上用 `GetConsoleMode`（不只是 `isatty`：NUL 设备会谎称自己是终端）。与策略规则互为纵深防御：`deny-boundkeep-state-commands` 里加了 `trust`（两份策略都加），agent 的每种 `boundkeep trust ...` 写法都被拒绝，**`trust list` 也一样**（规则只看得到子命令；你自己的终端里用 `trust list`，或用 `boundkeep doctor` 看列表）。`remove` 与 `list` 不要求终端（有测试）。
- `boundkeep doctor` 新增检查 `trusted-projects`：数量；非空时总有一行 `RISK:` 的 info；条目不存在、是符号链接 / junction 指向别处、或被另一条覆盖（多余）时是 WARN。
- 一个运行中的守护进程在下一个事件时读到新策略（冒烟里就是这样验证的，不需要重启）。

**(c) 开发工具的归一化（Bash 与 PowerShell 同一份契约）**

- Bash：`programs.py` 的 `DEVTOOLS`（`pytest ruff mypy black isort flake8 pylint`）、`DEVTOOL_RISKY_FLAGS`（按工具列出）、`devtool_form`，`bash.py` 做程序改写；PowerShell：`psprograms.py` 的 `DEV_TOOLS` 与 `pscmd.py`。
- 共同的契约：程序名在 `tool` 与 `python [无害选项] -m tool` 两种写法下**都是工具名**；`known`、`exec` 标签、**没有灰色原因、没有包装器标记**；路径限定的可执行文件把自己的路径作为读路径列出（所以规则能要求它在项目内）；加载或运行命令行上点名的文件或代码的选项保留为标志；带包装器（`sudo`、`uv run`、`poetry run`、`env`、`timeout`、`nohup`）的命令保留标记，所以 allow 规则永远匹配不到。
- 代码型环境变量前缀清单新增：`PYTEST_ADDOPTS`、`PYTEST_PLUGINS`、`PYLINTRC`、`PYTHONBREAKPOINT`、`PYTHONWARNINGS`、`PYTHONUSERBASE`（M1c 已有 `GIT_DIR`、`GIT_WORK_TREE`、`RIPGREP_CONFIG_PATH`、`XDG_CONFIG_HOME`、`LESS` 等）。
- **Bash 归一化器在同一行前面的命令可能写过文件时，拒绝信任路径限定的工具**（保持灰色 `program-path-qualified`）。
- `exec-of-written-file`（`event.py`）扩展：`mypy`、`pylint`、`flake8`、`pytest` 的配置文件（`mypy.ini`、`.pylintrc`、`.flake8`、`pytest.ini`、`setup.cfg`、`pyproject.toml`、`tox.ini`、`conftest.py` 等），以及 `pytest` 同一行里先写的测试文件（`test_*.py`、`*_test.py`）。**只管同一行**。

**(d) PowerShell 管道开头的修复**

- `pshelper.ps1` 在管道的后续各段的 `stage` 对象里带 `head`（开头表达式，普通元素；超过 4096 字符的字符串被截成"其他"元素，按动态处理）。
- 新的灰色原因 `ps-pipeline-head-dynamic`：开头是变量、子表达式、括号表达式等非纯常量。
- 纯常量字符串开头、下游是读文件的 cmdlet：开头成为读路径。**关闭了 `docs/powershell-dialect.md` 里的旧缺口 4**：`'~\.ssh\id_rsa' | Get-Content` 以前灰色且没有 deny，现在命中凭据保护规则被拒绝。

## 5. 偏差与风险

**集成时发现并已修的两件事**（都是主会话在把各部分合起来之后发现的）：

- **(a) 预算测试失败：每个事件解析了两次项目根。** 第一版在计算 `Action.project` 时又解析了一遍项目根，磁盘查询预算测试 `test_nothing_after_the_budget_touches_the_disk` 变成 4 次（预算 3 次）。修法：`event.py` 的 `_project_keys` 复用已解析的根与 cwd（cwd 就是项目根时不再做第二次查询）。
- **(b) 一个只在 Linux 上失败的测试假设。** 测试假设 `/usr/bin/python3` 在 Linux 容器里恰好是一个单独的路径引用，换了环境就不成立。修法：测试改成与环境无关。Linux 上该测试单独运行通过（16 个），但**完整 Linux 套件在这一行修改之后没有重跑**。

**对已有测试与语料的改动。** `tests/corpus/workflow_benign.yaml` 里 `pytest`、`python -m pytest -q`、`pytest tests/test_x.py -x` 等开发工具条目从 `t3-exec` 层移到新的 `t3-dev` 层（grep 到 28 条），带 `expect_trusted: allow`；`Get-Content src\app.py | Select-Object -First 20` 这类以命令开头的管道现在期望 allow（`allow-ps-data-shaping`）。`uv run pytest -q`、`npm test`、`cargo test` 等仍留在 `t3-exec`，期望不变。度量脚本里 M1c 的"before"一行把写 `mypy.ini` / `pytest.ini` / `.flake8` 算作 allow，现在是 ask（见第 6 节的说明）。

**残余风险**（每条都要当面说清）：

- **跨工具调用的"先写后运行"链无法识别。** 先 `Write` 写 `tests/test_x.py`，下一次调用再 `pytest`：各自都是 allow。`exec-of-written-file` 只看同一行。这是信任一个项目的代价，规格 §7 与 `docs/policy-reference.md` 已写明；会话污染标记（M3a）计划用来收紧它。`conftest.py`、`mypy.ini`、`pytest.ini` 等配置文件本身的写入是 ask，但 `tests/test_x.py` 不是。
- **受信任项目自己的代码不经审查地运行。** 包括项目里已有的 `conftest.py`、测试、pytest 插件、`pyproject.toml` 里的工具配置。信任等于相信这个仓库（以及它的依赖）。
- **合并的标志清单是保守的。** 规则只有一条，各工具的危险标志合并：某个工具的危险选项对七个工具一起生效，例如 `mypy -p pkg`（对 mypy 它只是包名）也会 ask，因为 `-p` 对 pytest 是插件。想精确可以拆成每工具一条规则，见第 8 节 #3。
- **`trust list` 对 agent 也是拒绝。** 因为规则只看得到子命令。你在自己的终端里用，或看 `boundkeep doctor`。
- **带包装器的永远不放行。** `uv run pytest`、`poetry run`、`sudo`、`env X=1 pytest`、`timeout 5 pytest`、`nohup` 保留包装器标记。这对你的 `uv run` 习惯是个代价：`uv run pytest` 仍然会问；直接用 `.venv\Scripts\pytest.exe` 或 `python -m pytest` 才能被放行。

## 8. 需要你决定的事项

1. **要不要把 boundkeep 仓库本身信任起来用于日常开发。** 优点：你的会话里 `.venv\Scripts\python.exe`、`ruff`、`mypy` 占 `program-path-qualified` 的大头，信任后它们才可能被放行。需要先明白两件事：（一）信任它就是让它自己的代码不经审查地运行（它是你自己写的，风险与"信任任何自己的仓库"相同）；（二）**`protect-guard-code` 仍然会挡住 agent 对 `src/boundkeep` 的编辑**，只要这个仓库同时是已安装的包（M1 起就这样：开发 boundkeep 本身要用 `audit-only`，或者另装一份用于开发）。信任与这一点无关，不会改变它。**建议**：先用第 7 节的 `--trust` 测一下，看数字再决定。
2. **要不要先对真实会话测一遍。** 命令在手工验收文档的 T8（`uv run python scripts\session_command_stats.py --since-days 60 --trust E:\boundkeep\boundkeep`，并与不带 `--trust` 的结果对比）。**建议先做**，它决定这个预设对你值不值。
3. **要不要把合并的 allow 规则按工具拆开。** 拆开后每个工具只被自己的危险标志管（`mypy -p pkg` 不再 ask），代价是 7 条规则、每条 `flags_none` 一份清单。当前一条合并规则更容易审查，也更保守。**建议**：先不拆，等真实数据显示这类误报确实常见。
4. **要不要把预设扩展到 node 工具**（`npm test`、`npx tsc`、`eslint` 等）。它们的配置与插件机制各不相同（`package.json` 脚本、`.npmrc`、预安装钩子），不能照搬 Python 的标志表。**建议**：不在这个里程碑做；要做的话另开一轮并同样需要独立的标志审查。
5. **定向 X1 审查。** 建议在 M2 之前做，覆盖新增面：`trusted_projects` 的加载器与匹配器（过宽判断、链接解析、cwd 在项目外）、`trust` CLI（文本编辑、`add` 的终端检查、原子写入）、开发工具的归一化（Bash 与 PowerShell 的契约是否一致、包装器与环境变量前缀）、`DEVTOOL_RISKY_FLAGS` 清单（是否漏了会加载或运行代码、写文件的选项）、管道开头的改动（`stage.head`、`ps-pipeline-head-dynamic`、常量开头成为读路径）、`exec-of-written-file` 的扩展。主会话会给审查提示词。
6. **提交方式**：A. 两个提交——① 代码、测试、策略、脚本；② 文档（本报告、手工验收、`policy-reference.md`、`powershell-dialect.md`、`PROJECT_SPEC.md`、`IMPLEMENTATION_PROMPTS.md`、`CLAUDE.md`）——然后打标签 `m1c2-done`（**建议**）；B. 一个提交。我没有提交，也没有推送。
