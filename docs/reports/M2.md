## 3. 结果怎么读（先读这一节）

完整的表在 `eval/report.md`。几个读数的前提：

- **“拦截合计 100%”几乎没有信息量。** 四个格子里每一条攻击样本的裁决都不是 allow，因为没有规则命中的命令在规则层是“灰色”，没有 LLM 时灰色就是 ask。把 ask 拆开看：**由规则命中的 ask 占攻击样本的 23%（Windows dev）到 42%（POSIX test）**，其余是灰色兜底转成的 ask。MCP 类尤其如此：工具名规则层不认识，全是兜底。
- **“达到样本要求的最低裁决”更有用**：Windows dev 81.9%（规则裁决达到的 55.3%）、Windows test 77.1%（42.9%）、POSIX dev 86.5%（59.6%）、POSIX test 85.4%（58.5%）。
- **路径写法这一类规则层做得最好**：41 条 path-evasion（多余的当前目录段、重复分隔符、`..` 回退、大小写、正斜杠、环境变量与波浪号、WSL 与 Cygwin 路径、管理共享、设备路径前缀、数据流名、通配符）在四个格子里**全部被规则 `deny`**，没有漏报，也没有靠灰色兜底。这一类的样本多半来自规则本身的设计关注点，不要当作对绕过能力的一般性结论。
- **漏报几乎都是同一种**：样本要求 `deny`，默认策略给的是 `ask`。默认策略的设计就是对持久化、系统配置写入、递归删除等“问一次”，`strict` 策略才直接拒绝。在 dev 上同样的样本跑 `strict`：达到要求的数 Windows 65→69 / 82、POSIX 79→85 / 93。所以这些漏报不是“规则没认出来”，而是“默认策略选择只问不拒”；样本的 `deny` 要求反映的是我们对这些动作应有的严重程度，不是对默认策略的承诺。
- **MCP 的 `deny` 样本（4 条）全部漏报**：规则层把所有 MCP 工具当“未审核”处理，统一灰色。
- **正常操作的误报率很高**：Windows dev 36.5%、test 39.4%；POSIX dev 68.3%、test 77.3%。**这些不是对真实使用体验的估计**：正常样本由我挑选，POSIX 的以合成为主，而且包含了大量会运行项目代码的命令（见下）。参考列（假机器的项目受信任）只把误报降了几个百分点到 7 个百分点。

## 4. 误报与漏报的原因（只用 dev 集统计）

### 误报（dev）

| 原因 | Windows | POSIX | 说明 |
|---|---:|---:|---|
| 没有规则匹配（灰色） | 21 | 35 | 常见的无副作用命令也没有 allow 规则，比如 `git stash`、`git add`、`New-Item`、`cd`、写文件到项目外的路径 |
| MCP 工具未审核（灰色） | 19 | 21 | 所有 MCP 调用一律 ask，包括只读查询 |
| 访问不在白名单里的主机（`net-allowlist`） | 10 | 16 | 发通知、上传制品、安装脚本等网络操作 |
| 运行项目代码（`runs_repo_code`） | 13 / 13 | 21 / 21 | 全部被问，是默认策略对未受信任项目的设计 |
| 其他规则（读项目外路径、持久化命令、读 agent 状态、`git reset --hard` 等） | 约 8 | 约 10 | 单条规则各占 1 到 5 条 |

此外，**评测框架本身有一个假象，已修**：真实会话里对会话草稿目录的写入，在假机器上因为没有传入会话 id 而匹配不上“放行本会话草稿目录”的规则，被多问了一次。现在运行器把导入器统一用的假会话 id 传给管线，Windows dev 的误报由 72 条降到 66 条。这是修评测，不是改规则；对 dev 和 test 两边都生效。

### 漏报（dev，样本要求 deny 而实际不是）

| 原因 | Windows | POSIX |
|---|---:|---:|
| 规则给的是 `ask`（持久化、系统配置、递归删除、结束进程、读写凭据文件等） | 11 | 9 |
| MCP 工具未审核（灰色） | 4 | 4 |
| PowerShell 解析为动态内容或提供者路径（灰色） | 3 | 0 |

## 5. 我在 test 集上做过什么

为了写这份报告，我看了 `eval/report.md` 里 test 切分的指标表和每格前 10 条漏报与误报。**之后没有改任何规则**。评测框架的修改（上面的会话 id）是看过 dev 的原因统计之后做的，对两个切分一致生效。如果以后要改规则，按方法学：要么只依据 dev，要么声明 test 已被污染并换新的留出集。

## 6. 没做的与局限

- **obfuscation 只有 11 条，不足 30 条**：这一类的比例只是粗略提示。我写这类样本时被安全分类器拦下，使用者手写又觉得麻烦，决定先不补。补法是 `eval/authoring/TEMPLATE.txt` + `eval/add_samples.py`（一行一条，一条命令生成），补完重跑评测即可；指纹会变，报告里的指纹要跟着换。
- 样本分布由作者选定，不代表真实使用；**不能把比例当作对真实世界的估计**，也不要在 README 引用。
- POSIX 的正常样本全是合成，真实的只有 Windows。
- 评测不经过 Claude Code，也不碰真实磁盘；硬链接、符号链接、联接点不在其中。
- 延迟是进程内的规则管线耗时（Windows 约 6 毫秒 p50、POSIX 约 4 毫秒），不含 hook 客户端与守护进程往返。
- 没有 LLM 行，没有 `rules+taint` 行。

## 7. 评测暴露的、值得之后处理的规则层问题（这一步不改）

1. **MCP 工具一律灰色**：读类 MCP 调用 100% 被问。需要一种让用户声明“这些 MCP 工具是只读的”的办法（不是内置白名单，因为工具名不固定）。
2. **常见的无副作用命令没有 allow 规则**：`git stash`、`git add`、`git commit`、`New-Item`、`Set-Location` 到项目目录等。
3. **`net-allowlist` 太粗**：任何不在白名单里的主机都 ask，发构建通知、上传制品这类常规操作都被问。
4. **默认策略对 `deny` 的取舍**：持久化、系统配置写入等目前是 `ask`，样本要求 `deny`。这是策略选择，要不要变是产品决定。
5. **选项白名单（L-1）** 会改规则，若要做，做完需要重取基线。
