# 威胁模型补充：会话状态与 LLM 审计层（M3a）

> 状态：2026-10-30，随 M3a 写成。范围内与范围外的威胁以 `PROJECT_SPEC.md` §3 为准；这里只写会话状态（任务意图、污染标记）与可选的 LLM 审计层**能做什么、做不到什么**。M3a 没有接过任何真实的 LLM 服务（只对本地假服务测过），所以 LLM 一节说的是代码的保证，不是任何模型的效果。

## 1. 污染标记能做什么

- **来源**：策略的 `taint.sources`（默认 `WebFetch`、`WebSearch`、`mcp__*`，以及读 MCP 资源的 `ListMcpResourcesTool`、`ReadMcpResourceTool`、`ReadMcpResourceDirTool`：它们的名字不以 `mcp__` 开头，2.1.304 的 hook 实测见 `docs/hook-behavior.md`；规格修订 7，P-F2）。来源工具的调用在 **PreToolUse 与 PostToolUse 两处**都打标记：hook 客户端在 PostToolUse 失败时什么也不做（没有决定可以降级），只靠它打标记就会失败即放行；PreToolUse 一定经过守护进程（守护进程不在时每个调用都会问）。在 PreToolUse 打标记可能把一次随后被拒绝的调用也算进去，这是安全的方向。
- **经 shell 读进来的外部内容**（规格修订 8，P-R5；X1 复审 R-5）：shell 调用里有动作带网络、而判决不是 deny 时，这次调用也是来源（来源名 `shell-network:<程序>`）：`gh issue view`、`curl`、`wget`、`Invoke-RestMethod`、`npm view`、`ssh 主机 命令`、`git ls-remote` 都算。只搬代码、只运行项目自己代码的子命令不算：`git clone|fetch|pull|push`，包管理器的安装、同步、构建子命令，以及 `npx <裸名字>`、`uv run`、`cargo run`、`go run .`（名单在 `session/sources.py`）。名单之外的一律算，漏掉的只会让会话多问。**运行注册表里的包算来源**（第二轮定向复审 S-2）：`pnpm dlx`、`pnpx`、`pnx`、`yarn dlx`、`create` 一族、`npm init <名字>`、`pipx run`、`uvx`、`uv tool run`、`uv run --with`、`uv run <URL>`、`go run <包>@<版本>`，以及带版本、带 scope、URL 或用了 `--package`、`--yes`、`--call` 的 `npx`、`bunx`、`npm exec`（带 scope 的本地依赖也算，多问）。这些调用带 `exec`，所以它们自己那次就给项目打标记。守护进程繁忙或超时、没有审查就回答的 shell 调用，也按来源记（`shell-unreviewed`）：没人看过它会不会读网页。配置了 LLM 后端时（PostToolUse 的 matcher 是 `*`），shell 调用在 PostToolUse 时再判一次，与来源工具一样在两处记（S-3）。残余：`npx cowsay` 这种裸名字分不出本地还是要下载，项目里没有时它下载并运行，批准之后会话不带污染（S-2）；运行代码自己去取的内容（解释器一行代码、项目里的脚本、.NET 的网络类）归一化层看不出网络，不算来源（S-4）；没有配置后端时 shell 调用没有 PostToolUse，守护进程不在线时被批准的 `gh issue view` 不会被记下；配置了后端也只有在工具运行完之前守护进程已经回来才记得下（S-3）。
- **窗口**：来源调用之后，会话一直是"被污染"的，直到 `taint.window`（默认 3）个被污染一步改成 ask 的调用**被用户批准、工具真的运行了**（规格修订 7，P-F6；修订 8，P-R3）。污染一步只管**不是规则给出的 allow**：LLM 审计的 allow（§9.5 的最后一步）与"什么都不碰的工具"的 allow，动作带 `taint.sensitive_tags` 里的标签时改为 ask。这次询问的 `tool_use_id` 被记下，同一个 id 的 PostToolUse 到达时才计一次（Claude Code 2.1.304 实测：被批准的调用有带同一个 id 的 PostToolUse，被拒绝的没有，`docs/hook-behavior.md`"M3a 复审的实测"）。所以被拒绝的询问、自动拒绝的询问（`dontAsk`、没人批准的 `claude -p`、看不到确认框的后台子 agent）都不计数，同一个被拒的动作问多少次都不会因窗口结束而放行。规则给出的 allow（项目内只读等）不受影响，也不计数（§7）；无害的调用（读文件、`ls`）用不掉窗口（X1 审查 F6）。`audit-only` 下不问任何人，也不计数。配置了 LLM 后端时 `init` 把 PostToolUse 的 matcher 写成 `*`，否则同一个 id 的结果到不了守护进程；没有后端时污染一步实际不会改出 ask，matcher 仍只列来源。
- **粘性位**：会话里只要调用过任一来源，`session_read_untrusted` 就一直成立，直到这个会话结束（`/clear` 换新的 `session_id`；resume、continue、compact 不换，`docs/hook-behavior.md` E9）。**fork**（`--fork-session`、桌面应用的 fork）换新的 `session_id`，SessionStart 的 `source` 是 `fork`，不带父会话的 id（2.1.304 实测），所以 boundkeep 认不出它来自哪个会话：`init` 注册 SessionStart，`source` 不是 `startup` 或 `clear`、而 id 不在库里的会话（fork、清理之后 resume 的会话）按读过不可信内容开始（来源名 `inherited:<source>`；修订 8，P-R9）。新会话（`startup`、`clear`）在库里记一行干净的状态，之后的 resume 与 compact 都认得它。代价：从干净会话 fork 出来的会话也被当作读过不可信内容。**漏记 SessionStart 的会话**（修订 9，P-S1；第二轮定向复审 S-1）：所有安装记录都注册了 SessionStart 时，PreToolUse 或提示词遇到库里没有的 id，这个会话也按读过不可信内容开始（来源名 `inherited:unknown`），但只有这一个来源时它的写不打项目标记；随后到达的 `startup`、`clear` 把它改回干净。守护进程晚于会话启动时，那个会话里的开发工具因此再问。默认策略与 strict 策略用它加了一条 ask 规则 `ask-devtools-after-untrusted-content`：会话读过网页、搜索结果或 MCP 返回值之后，`pytest`、`ruff`、`mypy` 等会运行项目代码的开发工具一律再问，受信任项目也一样。这就是 X1 审查 M-2 的"先写后运行"链：被注入的 agent 先写一个测试文件（项目内写入，放行），再运行 pytest（受信任项目里放行）。用粘性位而不是窗口，是因为窗口会过去（被问过 `window` 次之后）。
- **项目上的标记**（规格修订 7，P-F1；X1 审查 F1）：粘性位只在会话里，写进项目的文件却留在项目里。读过不可信内容的会话（粘性位为真或状态未知）里，一次调用只要有一个动作可能写（访问方式 `write` 或 `unknown`）：路径不确定在项目之外时，记下这个动作的项目目录，会话的工作目录在项目之外（比如 `cd` 进了附加的工作目录）时也一样（X1 复审 R-1）；路径确定在项目之外时（写进别的项目），记下路径本身；但写到项目之外的开发工具配置文件（`pytest.ini`、`.pylintrc`、`conftest.py`、`pyproject.toml` 等，名单在 `session/marks.py`）记它所在的目录，`~/pytest.ini` 让主目录下的项目都带标记（修订 8，P-R7），写在盘符根或文件系统根（`E:\pytest.ini`、`/pytest.ini`）时记"所有位置"，只有 `taint clear --all` 能解除（修订 9，P-S6）。`enforce` 下规则判决是 deny 的调用不打标记，它不会运行（修订 9，P-S7）；被问的调用仍然打，用户拒绝了也一样，LLM 的 deny 也仍然打（标记在送审之前写）。`boundkeep taint list` 显示打标记的调用属于哪一类（写、看不到路径的写、运行代码）。看不到写路径的写也记项目目录（修订 8，P-R6）：规则没有放行的、会运行代码的动作（`python gen.py`、`make generate`），带写标签却没有可写路径的动作，写文件的 MCP 工具（工具名的动词不是读），会改工作区的 `git` 子命令（`stash pop|apply|branch`、`checkout`、`switch`、`restore`、`apply`、`am`、`merge`、`pull`、`reset`、`cherry-pick`、`rebase`、`revert`、`bisect`、`sparse-checkout`、`checkout-index`、`worktree add`、`submodule update|add`、`read-tree -u`，规则放行了也记），以及规则没放行的、程序表里没有的 `git` 子命令（别名 `git co`、外部命令 `git foo`，第二轮定向复审 S-5）。来源调用按它之前的状态判，打标记却按它之后的状态，所以会话里第一个来源调用自己的写（写文件的 MCP 工具、`curl -o tests/x.py`）也记。标记存在会话状态库里，不随会话清理删除，也不按时间过期。默认与 strict 策略的 ask 规则 `ask-devtools-after-untrusted-project-write`（匹配字段 `project_written_after_untrusted`）让开发工具在带标记的项目里一律再问，**不管是哪个会话**。只有用户在终端运行 `boundkeep taint clear` 才解除：它与 `trust add` 一样拒绝在 Claude Code 启动的进程里或没有真实控制台时运行，agent 的 `boundkeep taint ...` 被 `deny-boundkeep-state-commands` 拒绝。标记读不出时算命中；超过 1000 个位置时记一个"所有位置"的标记。
- **子 agent**：子 agent 的事件带父会话的 `session_id`（夹具 `PreToolUse__PowerShell_in_subagent`），子 agent 读的网页同样污染主会话。
- **持久**：状态在 `~/.boundkeep/session.sqlite`，守护进程重启不丢；30 天没有活动的会话被清理，会话数超过 5000 时最久没活动的先被清掉。30 天对齐 Claude Code 自己的默认：它把会话记录在本机保留 30 天以便 resume（`cleanupPeriodDays`，官方文档 data-usage 页，2026-10-30 读取）。**例外**：在 Claude Desktop 或 Cowork 里开始或最近继续的会话默认不受那个期限限制，在那里 resume 一个 30 天以前的会话时，boundkeep 已经没有它的污染标记；改大了 `cleanupPeriodDays` 的用户同理。

## 2. 污染标记做不到什么（已知局限）

- **来源按工具名与 shell 里的网络动作识别**（规格 §7；修订 8 之前只按工具名）。仍然不打标记的：读一个不可信的本地文件（下载的 README、issue 的导出、别人发来的补丁），`git clone` / `git pull` / `git fetch` 拿到的仓库内容（只搬代码，例外名单），之后用本地命令读它（`git log -p origin/...`），裸名字的 `npx cowsay` 下载并运行的包的输出（第 1 节），以及安装脚本与 git 输出里远端写的文字（被接受的残余）。
- **服务端工具**：M0a 实测 `WebFetch`、`WebSearch` 都触发 PreToolUse 与 PostToolUse（E13，用户报告的 #93182 没有复现），所以它们能打标记；以后的 Claude Code 版本若改变这一点，`PreToolUse` 那一处仍然会打。
- **`@` 引用**：用 `@` 加进提示的文件不经过任何工具调用（规格 §3），既不经规则，也不打标记。
- **守护进程没在运行的那段时间**：那段时间里每个工具调用都会问（失败即关闭），但用户同意了的来源调用不会被记下；守护进程之后再起来，会话被当作干净的。例外是工具运行完之前守护进程已经回来：来源工具的 PostToolUse 总能补记，shell 调用只有配置了 LLM 后端时才能（S-3）。SessionStart 也没有可以降级的决定（修订 8，P-R9）：守护进程在会话开始时不在、或那次写库失败时，所有安装记录都注册了 SessionStart 的安装里，这个会话按 `inherited:unknown` 开始（修订 9，P-S1；第 1 节）。残余有两处：有旧安装记录时它仍从干净状态开始，这是失败即放行的一处（`doctor` 检查 SessionStart 是否注册）；漏记 SessionStart 的 fork 只在自己会话里再问，它的写不打项目标记，别的会话看不到。已经在库里的会话，中途守护进程不在时被批准的来源仍然记不下。升级之前开始的会话库里没有记录，第一次 resume 或 compact 时按读过不可信内容开始（多问一阵）。agent 团队里接收主会话转述内容的队友（新 id，SessionStart 的 `source` 未测）不在这条规则之内。
- **会话状态库不可用**（损坏、磁盘满、权限）时，每个调用都按"状态未知"判，即当作已污染（失败即关闭）：开发工具都会问，LLM 的 allow 对敏感动作都变成 ask。守护进程启动时与 `ping` 的状态里会说明。
- **粘性位只覆盖开发工具名单**。别的会运行项目代码的命令（`make`、`npm test`、`./build.sh`、`python 脚本`）在默认策略里本来就没有 allow 规则（灰色，没有 LLM 时就是 ask）；**配置了 LLM 后端时，它们交给 LLM**，被污染的窗口内带敏感标签的会转成 ask，窗口过了之后就是模型说了算，除非项目带标记（修订 8，P-R2，见下）。M3a 把"表里没有的程序"、包管理器与任务运行器（`npm`、`uv`、`make`、`cargo` 等）、未知工具与 MCP 调用统一标成 `exec`，所以它们在窗口内一定算敏感动作。经包管理器启动的开发工具（`pipenv run pytest`、`conda run pytest`、`poetry run pytest`）在规则层看到的程序是包管理器，**不受粘性规则约束**，窗口过了之后同样交给模型。
- **没有审查就回答的调用**（守护进程繁忙，或请求在排队时就超时）仍给来源工具打标记，在单独的线程里做，尽力而为。
- **窗口按被批准的污染询问计数，不按时间**：长时间不动的会话，窗口不会自己过期；同一个会话里并行的调用可能都在窗口之内判（计数在 PostToolUse 时写，保守）。窗口过去之后（用户批准过 `window` 次），LLM 对敏感动作的 allow 照常放行，直到下一次来源调用。用户每次都点"同意"也会让窗口过去：窗口只保证用户被问到，不替用户判断。PostToolUse 没到、失败或 matcher 不对（配置了 LLM 却没重新 `init`）时不计数，会话一直被污染（多问）。
- **标记进 LLM 路径**（修订 8，P-R2；X1 复审 R-2）：带标记的项目里，带 `exec` 标签的灰色调用（`npm test`、`make test`、`python -m unittest`、`tox`）不发给模型，直接问（`decided_by: gray-marked-project`），不管是哪个会话；标记读不出时也一样。**与 P-R6 合起来的效果**：读过不可信内容的会话里，第一次运行会运行代码的灰色命令就会给项目打标记，之后这个项目里所有会运行代码的灰色命令都不送审、直接问，直到用户 `taint clear`；窗口对它们不再起作用，只对其余敏感动作（写文件、网络外发）还有意义。规则 deny 的调用不再有这个效果（修订 9，P-S7），但**被问、用户拒绝的调用仍然有**：被注入的 agent 可以用一次会被拒绝的调用让项目带上标记，让询问变多（第二轮定向复审 S-7 的残余）；配置了 LLM 时，这类调用推迟到 PostToolUse 才打标记能解决它，代价是 PostToolUse 丢失时没有标记，所以没有做。没有配置后端时没有变化（灰色本来就问）。
- **项目标记来自看得到的调用**：被规则直接放行、又不带写路径、也不在 git 名单里的命令写下的东西（开发工具自己生成的文件、缓存）不打标记；会话之外的写（用户自己的编辑器、别的进程）也不打。用户级的配置位置（`~/.config/mypy/config`、`%APPDATA%` 下的配置）与可编辑安装的兄弟项目（`pip install -e ../lib` 之后写 `../lib`）只记文件本身，读它们的项目看不到（这些写在会话 A 里本身要问）。守护进程繁忙或超时、没有审查就回答的调用不打项目标记（来源调用照样打污染标记）；策略文件坏掉时也不打（那时每个调用都问）。标记只看项目目录：同一个项目里，写测试文件的会话与运行 `pytest` 的会话不必是父子关系。`trusted_projects` 有条件推荐（使用者 2026-11-01 决定）：默认仍是空列表，只信任自己写过或审计过的仓库；第二轮定向复审 `docs/reviews/M3a-rereview-2.md` 没有高危、中危，残余见那份报告第 3 节与 `docs/reports/M3a-closeout.md` 第 5 节。
- **任务意图只在配置了 LLM 后端时才存**：没有后端时没有谁读它，提示词摘录就不落盘。

## 3. LLM 审计层的保证（代码层面，不是模型效果）

- **只审规则判不了的**：规则 deny / ask / allow 的动作都不会发给模型；模型永远不能把规则的 deny 或 ask 改松。
- **只审被完整分析过的**：归一化的预算用完、解析器内部错误、PowerShell 辅助进程不可用、子树扫描超限、MCP 参数没看全或带命令、程序名 / 路径 / 主机 / MCP 工具名一个都没认出来时，调用不发给模型，直接 ask（模型只能看到一部分，它的 allow 会覆盖没人看过的部分）。
- **只审请求能完整展示的**（M3a 的 X1 审查 F3、F4，`pipeline.unshown_input`，规格文字待定，见 `docs/reports/M3a-review-fixes.md` 第 7 节）：请求里只有每个命令的词、路径与主机。下面这些调用的代码或参数不在请求里，所以同样不发、直接 ask：here-document 与 here-string（`python3 <<EOF` 的代码、`psql <<EOF` 的 SQL；交给 shell 的除外，它们被解析成了单独的命令）；`NAME=value` 赋值（命令前缀、`env NAME=v`、单独的赋值语句，如 `NODE_OPTIONS`、`DATABASE_URL`）；PowerShell 里管道进解释器的字符串与赋值语句；MCP 调用（参数不发给模型）。代价：配置了后端时，这些调用与没有后端时一样都要问（`cat <<EOF > 文件` 这类写法也在内）。
- **带标记的项目里，会运行代码的调用不审**（规格修订 8，P-R2）：一次灰色调用里有带 `exec` 标签的动作、而它的项目带标记（标记读不出也算）时，不发给模型，直接 ask（`decided_by: gray-marked-project`）。读过不可信内容的会话写进项目的东西，另一个干净会话的模型看不到，它的 allow 就是结果。
- **碰到 Windows 设备路径的调用不审**（规格修订 10，`pipeline.device_path`）：key 在 `//./` 之下时，key 说不清它通向哪里（`\\.\GLOBALROOT\Device\Mup\...` 是网络共享，`\\.\pipe\x` 是本机上监听的程序，`\\.\C:` 是整个卷，`//./aux` 也可能是项目里的 `aux.py`），模型放行的只是一串字符，所以不发给模型，直接 ask（`decided_by: gray-device-path`）。UNC 的 `pipe`、`mailslot`、`ipc$` 也算（修订 11）。只有 shell 命令里的裸名字 `NUL` 和只带前缀的写法例外：带目录或盘符的写法可能是普通文件，模型和缓存分不清（修订 11）。残余：文件名恰好是设备名的路径，key 藏住了真实位置，按路径写的 deny 规则匹配不到，结果是问，不是 deny；卷是问，不是 deny（`docs/reports/M3a-device-paths.md` 第 6 节）。其余见 `docs/reports/M3a-path-gate-fixes.md` 第 6 节。
- **路径的读法因程序而异**（规格修订 11 到 13）：同一串字符，PowerShell 5.1 打开 `keys`，Git Bash 和 Node 打开 `keys.`；Git Bash 里 `work:s` 是另一个目录，别的程序里是流。这种路径 `inside_project` 不说 True，allow 规则用不上；但磁盘还是要查，两种读法都查，否则项目里的联接点就能藏住 deny 规则点名的目标（`docs/reports/M3a-readings-fixes.md`）。主机名不经 `casefold` 或 IDNA 算成本机：`\\localhoſt\c$\x` 不是本机的 C 盘，Windows 会去解析这个名字。残余：大小写敏感的目录里 `WORK` 和 `work` 的 key 相同（`docs/reviews/M3a-dots-and-folding-review.md` RV-4）。
- **只发结构化字段**（`audit/send_gate.py`）：工具名、归一化后的动作（程序、子命令、选项、词、路径、主机、风险标签、规则判不了的原因）、是否在项目内、污染位与来源工具名、任务意图摘要。不发文件内容、工具输出、原始命令行、工作目录；路径写成 `<project>/…` 或 `~/…`；用守护进程的环境展开过变量的路径按原文（`$GITHUB_TOKEN/x`）发，不发展开值；整个负载先过字段白名单，再整体脱敏。
- **看不全或可能带秘密就不发**：动作太多、词太多或太长、负载超过 16000 字符、路径或词里有控制字符或格式字符（双向覆盖、零宽字符、终端转义）；秘密要把几个词连起来才看得出（`--password X`、`curl -u user:pw`）；序列化之后再脱敏一遍会变（脱敏器的模式是为 shell 文本写的，在 JSON 上的改动不可信，所以不改了再发，而是不发）；请求里出现守护进程环境里名字像秘密的变量的值（含 `api_key_env` 指向的那个）。一律不发，直接按 `on_failure` 处理。截断后的视图可能把要紧的部分藏在填充后面，而模型只能放行它看见的东西。
- **模型的输出不被信任**：必须恰好是五个字段、类型与长度都对、合法 JSON、没有重复键（`{"verdict":"deny","verdict":"allow"}` 这种写法算无效）；任何不符都是 `invalid_output`，不尝试修复。最终判决由代码按 §9.5 计算：偏离任务或风险 ≥ 2 至少 ask，风险 3 一律 deny，被污染窗口内的敏感动作不能 allow。
- **模型的文字不回到 agent 的上下文**：给 Claude Code 的理由只由结构化字段（风险、是否偏离、是否被污染）组成；模型写的 `reasoning` 与 `reason_for_user` 只进审计日志（清洗、截断）。否则一个被命令文本操纵了的模型可以借理由对 agent 说话。
- **任何失败都是 `on_failure`**（默认 ask，可设 deny，永远不是 allow）：超时、限流、5xx、4xx、认证失败、网络错误、无效输出、后端没实现、发送出口拒绝、预算之后才到的回答、内部异常。
- **出站目标**：只允许 https（本机回环地址除外）；不跟随任何重定向；只接受未压缩的回答，最多 256 KiB；一次审计的总预算是 `timeout_ms`，最多 6 秒，是整次尝试（名字解析、连接、TLS、响应头、响应体）的硬期限，逐字节滴发响应头的服务拖不长它；卡住的名字解析在后台线程里自己结束，审计不等它（同时最多 8 个，再多就直接按 `network` 失败；X1 审查 F5）；最多重试一次，只针对超时、限流、5xx、网络错误，且剩余预算足够时，限流时的 `Retry-After` 不是不超过 2 秒的纯秒数就不重试。错误信息不含请求体、回答体与密钥；密钥只从 `api_key_env` 指定的环境变量读，只放在请求头里。
- **守护进程的期限**：带 LLM 审计的审查期限是规则的 2 秒加预算再加 0.5 秒，从请求提交时算（排队的请求也有）；超时时 enforce 下按 `on_failure` 回答。

## 4. LLM 审计层做不到什么

- **不能识别"看起来和任务相符"的恶意动作**，如果规则也认不出来。规则层仍然是第一道、也是确定性的一道；模型只处理灰色地带，而它的判断质量 M3a 没有测过（M3b 的事）。
- **间接运行 boundkeep 的状态命令**（`mode`、`uninstall`、`init`、`serve`、`trust`、`taint`）：`deny-boundkeep-state-commands` 认得出 `boundkeep`、`boundkeep.exe`、`python -m boundkeep` 及其模块（`boundkeep.cli`、`boundkeep.__main__`，X1 复审 R-4）、`uv run` / `uvx` / `pipx run` 这些启动方式，以及程序名或启动器名结尾带点或空格的路径（`& '…\boundkeep.exe.'`，PowerShell 5.1 照样运行它，实测；规格修订 16）、最后一段是 8.3 短名且磁盘上解析得出长名的路径（`& '…\BOUNDK~1.EXE'`；规格修订 17；Git Bash 里不带 `.EXE` 的 `'…/BOUNDK~1'` 也认得，修订 18）；经 PATH 运行的裸短名（Git Bash 里的 `BOUNDK~1 mode audit-only`）认不出是哪个程序，是灰色，不送审，总是问（修订 18）；带路径而磁盘上解析不出长名的短名也一样（修订 19，复审 R18-4），例如 `cd` 进路径里带短名的目录之后的 `./BOUNDK~1`、`.\BOUNDK~1.EXE`，两种 shell 都运行它们（实测）；更间接的写法认不出，是灰色：`python -c "from boundkeep.cli import main; …"`、`python -m runpy boundkeep …`、按路径运行 `cli.py`、`cmd /c`、`Start-Process`、`bash -c`。没有 LLM 时它们问用户；配置了 LLM 时由模型判断（命令文字在请求里）。`trust add` 与 `taint clear` 另有运行时的两道检查，`mode` 与 `uninstall` 没有。
- **任务意图本身可能被污染**：用户自己粘贴的文字不进任务意图（只留一个标记和长度），但用户亲手打的字如果是照着网页抄的，模型无从分辨。
- **缓存**：同一个问题（同样的动作、意图、污染位、后端、模型、提示词版本）10 分钟内（`cache_ttl_s`）直接用上次的模型结论，代码仍然重新裁决一次。缓存只在内存里。
- **同一用户的其他进程**能冒充守护进程、读写 `session.sqlite`、改环境变量里的密钥；这些都在规格 §3 的范围外。
- **带修订号的 `git diff` 能打印全部已提交的内容**（规则层的已知缺口，独立复审 IR-7，2026-11-07 记下；**2026-11-10 使用者决定记为接受的残余**，不修）：
  - `allow-git-read-only` 放行 `git diff`，而 `diff` 不像 `show`、`log -p` 那样扫描工作区。所以 `git diff <空树> HEAD`、`git diff <空树>` 由规则放行，实测打印出每个已跟踪文件的全文，包括 `.env` 和私钥。
  - 同样的内容，`git show HEAD`、`git log -p`、`git show HEAD:.env` 在项目里有受保护名字时是 deny。
  - `docs/reports/M2-rules-1.md` 原来只写了"已跟踪的 `.env` 被改过之后会被 `git diff` 显示"，实际范围更宽：任何已提交的内容、包括历史里的，都能这样打印。
  - 收紧它（带修订号的 `diff` 也扫描工作区）会让 `git diff HEAD~1` 在任何有受保护文件的项目里被拒绝。
  - 为什么接受（`docs/reviews/M3a-rev18-review.md` 第 5 节的建议，使用者采纳）：
    - `git diff HEAD~1` 这类写法太常用，而规则层看不出一个修订号离 HEAD 有多远，分不清它和空树那一种；
    - 受保护的文件一般不提交进仓库，`.env` 通常在 `.gitignore` 里，而 git 的这些命令只打印已提交或已跟踪的内容；
    - 读到的内容要离开本机，还要经过网络那一组规则。
  - 后果：只要这一条不改，git 打印已提交内容的同类写法，即使修了，也不减少 agent 实际能读到的内容。所以这类写法记在这一条下面，不单独修。修订 17 修的 `--` 之前的 pathspec 魔法、修订 18 修的 `git diff HEAD:src`（复审 R17-1）已经收紧了，不回退。
  - 记在这里的同类写法，都由规则放行，实测都打印了受保护文件（复审 `docs/reviews/M3a-rev18-review.md`）：
    - R18-1：工作目录在子目录时，`git diff HEAD~1:secrets HEAD:secrets`（两棵子树的扫描按当前目录算，git 从仓库顶层读）；
    - R18-2：花括号里带冒号的修订号，`git show 'HEAD@{10:00}'`、`git show 'HEAD^{/fix: typo}'`，PowerShell 里还有 `git show 'HEAD@{2026-11-09 10:00:00}'`（被当成 `REV:PATH`，不扫描）；
    - R18-3：`git log -p --full-diff -- sub`、`git show --full-diff HEAD~1 -- sub`（只读 pathspec，git 打印这些提交的全部改动）。
  - 如果以后要收紧这一条，R18-1 到 R18-3 要一起处理，修法见复审报告。
