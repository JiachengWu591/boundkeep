# 威胁模型补充：会话状态与 LLM 审计层（M3a）

> 状态：2026-10-30，随 M3a 写成。范围内与范围外的威胁以 `PROJECT_SPEC.md` §3 为准；这里只写会话状态（任务意图、污染标记）与可选的 LLM 审计层**能做什么、做不到什么**。M3a 没有接过任何真实的 LLM 服务（只对本地假服务测过），所以 LLM 一节说的是代码的保证，不是任何模型的效果。

## 1. 污染标记能做什么

- **来源**：策略的 `taint.sources`（默认 `WebFetch`、`WebSearch`、`mcp__*`，以及读 MCP 资源的 `ListMcpResourcesTool`、`ReadMcpResourceTool`、`ReadMcpResourceDirTool`：它们的名字不以 `mcp__` 开头，2.1.304 的 hook 实测见 `docs/hook-behavior.md`；规格修订 7，P-F2）。来源工具的调用在 **PreToolUse 与 PostToolUse 两处**都打标记：hook 客户端在 PostToolUse 失败时什么也不做（没有决定可以降级），只靠它打标记就会失败即放行；PreToolUse 一定经过守护进程（守护进程不在时每个调用都会问）。在 PreToolUse 打标记可能把一次随后被拒绝的调用也算进去，这是安全的方向。
- **窗口**：来源调用之后，会话一直是"被污染"的，直到污染一步已经把 `taint.window`（默认 3）个调用改成了 ask（规格修订 7，P-F6）。污染一步只管**不是规则给出的 allow**：LLM 审计的 allow（§9.5 的最后一步）与"什么都不碰的工具"的 allow，动作带 `taint.sensitive_tags` 里的标签时改为 ask，并用掉一次窗口。规则给出的 allow（项目内只读等）不受影响，也不计数（§7）。所以要让窗口过去，用户得被问 `window` 次；无害的调用（读文件、`ls`）用不掉它（X1 审查 F6）。`audit-only` 下不问任何人，也不计数。
- **粘性位**：会话里只要调用过任一来源，`session_read_untrusted` 就一直成立，直到这个会话结束（`/clear` 换新的 `session_id`；resume、continue、compact 不换，`docs/hook-behavior.md` E9）。默认策略与 strict 策略用它加了一条 ask 规则 `ask-devtools-after-untrusted-content`：会话读过网页、搜索结果或 MCP 返回值之后，`pytest`、`ruff`、`mypy` 等会运行项目代码的开发工具一律再问，受信任项目也一样。这就是 X1 审查 M-2 的"先写后运行"链：被注入的 agent 先写一个测试文件（项目内写入，放行），再运行 pytest（受信任项目里放行）。用粘性位而不是窗口，是因为窗口会过去（被问过 `window` 次之后）。
- **项目上的标记**（规格修订 7，P-F1；X1 审查 F1）：粘性位只在会话里，写进项目的文件却留在项目里。读过不可信内容的会话（粘性位为真或状态未知）里，一次调用只要有一个动作可能写（访问方式 `write` 或 `unknown`）：路径不确定在项目之外时，记下这个动作的项目目录，会话的工作目录在项目之外（比如 `cd` 进了附加的工作目录）时也一样（X1 复审 R-1）；路径确定在项目之外时（写进别的项目），记下路径本身。标记存在会话状态库里，不随会话清理删除，也不按时间过期。默认与 strict 策略的 ask 规则 `ask-devtools-after-untrusted-project-write`（匹配字段 `project_written_after_untrusted`）让开发工具在带标记的项目里一律再问，**不管是哪个会话**。只有用户在终端运行 `boundkeep taint clear` 才解除：它与 `trust add` 一样拒绝在 Claude Code 启动的进程里或没有真实控制台时运行，agent 的 `boundkeep taint ...` 被 `deny-boundkeep-state-commands` 拒绝。标记读不出时算命中；超过 1000 个位置时记一个"所有位置"的标记。
- **子 agent**：子 agent 的事件带父会话的 `session_id`（夹具 `PreToolUse__PowerShell_in_subagent`），子 agent 读的网页同样污染主会话。
- **持久**：状态在 `~/.boundkeep/session.sqlite`，守护进程重启不丢；30 天没有活动的会话被清理，会话数超过 5000 时最久没活动的先被清掉。30 天对齐 Claude Code 自己的默认：它把会话记录在本机保留 30 天以便 resume（`cleanupPeriodDays`，官方文档 data-usage 页，2026-10-30 读取）。**例外**：在 Claude Desktop 或 Cowork 里开始或最近继续的会话默认不受那个期限限制，在那里 resume 一个 30 天以前的会话时，boundkeep 已经没有它的污染标记；改大了 `cleanupPeriodDays` 的用户同理。

## 2. 污染标记做不到什么（已知局限）

- **只按工具名识别来源**（规格 §7 写明的 v0 局限）。Bash 的 `curl` / `wget`、PowerShell 的 `Invoke-WebRequest` / `Invoke-RestMethod`、`git clone` / `git pull` 拿到的仓库内容、读一个不可信的本地文件（下载的 README、issue 的导出）**都不打标记**。这些命令本身大多会被规则问（网络命令、未知主机），但用户同意之后，读到的内容不会让会话变成"被污染"。
- **服务端工具**：M0a 实测 `WebFetch`、`WebSearch` 都触发 PreToolUse 与 PostToolUse（E13，用户报告的 #93182 没有复现），所以它们能打标记；以后的 Claude Code 版本若改变这一点，`PreToolUse` 那一处仍然会打。
- **`@` 引用**：用 `@` 加进提示的文件不经过任何工具调用（规格 §3），既不经规则，也不打标记。
- **守护进程没在运行的那段时间**：那段时间里每个工具调用都会问（失败即关闭），但用户同意了的来源调用不会被记下；守护进程之后再起来，会话被当作干净的。M3a 不注册 SessionStart hook，所以分不清"新会话"和"状态丢了的旧会话"。
- **会话状态库不可用**（损坏、磁盘满、权限）时，每个调用都按"状态未知"判，即当作已污染（失败即关闭）：开发工具都会问，LLM 的 allow 对敏感动作都变成 ask。守护进程启动时与 `ping` 的状态里会说明。
- **粘性位只覆盖开发工具名单**。别的会运行项目代码的命令（`make`、`npm test`、`./build.sh`、`python 脚本`）在默认策略里本来就没有 allow 规则（灰色，没有 LLM 时就是 ask）；**配置了 LLM 后端时，它们交给 LLM**，被污染的窗口内带敏感标签的会转成 ask，窗口过了之后就是模型说了算。M3a 把"表里没有的程序"、包管理器与任务运行器（`npm`、`uv`、`make`、`cargo` 等）、未知工具与 MCP 调用统一标成 `exec`，所以它们在窗口内一定算敏感动作。经包管理器启动的开发工具（`pipenv run pytest`、`conda run pytest`、`poetry run pytest`）在规则层看到的程序是包管理器，**不受粘性规则约束**，窗口过了之后同样交给模型。
- **没有审查就回答的调用**（守护进程繁忙，或请求在排队时就超时）仍给来源工具打标记，在单独的线程里做，尽力而为。
- **窗口按污染一步的询问计数，不按时间**：长时间不动的会话，窗口不会自己过期；同一个会话里并行的调用可能都在窗口之内判（计数在判决之后写，保守）。窗口过去之后（用户被问过 `window` 次），LLM 对敏感动作的 allow 照常放行，直到下一次来源调用。用户每次都点"同意"也会让窗口过去：窗口只保证用户被问到，不替用户判断。
- **项目标记只认得出写路径的写**：运行代码的命令（`python gen.py`、`make`）与写文件的 MCP 工具，如果没有可见的写路径，它们写下的东西不打标记。这些命令在被污染的会话里本身是灰色（没有 LLM 时问用户；有 LLM 时在窗口内经过污染一步，窗口过去之后由模型判断）。守护进程繁忙或超时、没有审查就回答的调用不打项目标记（来源调用照样打污染标记）；策略文件坏掉时也不打（那时每个调用都问）。标记只看项目目录：同一个项目里，写测试文件的会话与运行 `pytest` 的会话不必是父子关系。`trusted_projects` 是否因 F1 的修复改为推荐设置，等定向复审之后由使用者决定。
- **任务意图只在配置了 LLM 后端时才存**：没有后端时没有谁读它，提示词摘录就不落盘。

## 3. LLM 审计层的保证（代码层面，不是模型效果）

- **只审规则判不了的**：规则 deny / ask / allow 的动作都不会发给模型；模型永远不能把规则的 deny 或 ask 改松。
- **只审被完整分析过的**：归一化的预算用完、解析器内部错误、PowerShell 辅助进程不可用、子树扫描超限、MCP 参数没看全或带命令、程序名 / 路径 / 主机 / MCP 工具名一个都没认出来时，调用不发给模型，直接 ask（模型只能看到一部分，它的 allow 会覆盖没人看过的部分）。
- **只审请求能完整展示的**（M3a 的 X1 审查 F3、F4，`pipeline.unshown_input`，规格文字待定，见 `docs/reports/M3a-review-fixes.md` 第 7 节）：请求里只有每个命令的词、路径与主机。下面这些调用的代码或参数不在请求里，所以同样不发、直接 ask：here-document 与 here-string（`python3 <<EOF` 的代码、`psql <<EOF` 的 SQL；交给 shell 的除外，它们被解析成了单独的命令）；`NAME=value` 赋值（命令前缀、`env NAME=v`、单独的赋值语句，如 `NODE_OPTIONS`、`DATABASE_URL`）；PowerShell 里管道进解释器的字符串与赋值语句；MCP 调用（参数不发给模型）。代价：配置了后端时，这些调用与没有后端时一样都要问（`cat <<EOF > 文件` 这类写法也在内）。
- **只发结构化字段**（`audit/send_gate.py`）：工具名、归一化后的动作（程序、子命令、选项、词、路径、主机、风险标签、规则判不了的原因）、是否在项目内、污染位与来源工具名、任务意图摘要。不发文件内容、工具输出、原始命令行、工作目录；路径写成 `<project>/…` 或 `~/…`；用守护进程的环境展开过变量的路径按原文（`$GITHUB_TOKEN/x`）发，不发展开值；整个负载先过字段白名单，再整体脱敏。
- **看不全或可能带秘密就不发**：动作太多、词太多或太长、负载超过 16000 字符、路径或词里有控制字符或格式字符（双向覆盖、零宽字符、终端转义）；秘密要把几个词连起来才看得出（`--password X`、`curl -u user:pw`）；序列化之后再脱敏一遍会变（脱敏器的模式是为 shell 文本写的，在 JSON 上的改动不可信，所以不改了再发，而是不发）；请求里出现守护进程环境里名字像秘密的变量的值（含 `api_key_env` 指向的那个）。一律不发，直接按 `on_failure` 处理。截断后的视图可能把要紧的部分藏在填充后面，而模型只能放行它看见的东西。
- **模型的输出不被信任**：必须恰好是五个字段、类型与长度都对、合法 JSON、没有重复键（`{"verdict":"deny","verdict":"allow"}` 这种写法算无效）；任何不符都是 `invalid_output`，不尝试修复。最终判决由代码按 §9.5 计算：偏离任务或风险 ≥ 2 至少 ask，风险 3 一律 deny，被污染窗口内的敏感动作不能 allow。
- **模型的文字不回到 agent 的上下文**：给 Claude Code 的理由只由结构化字段（风险、是否偏离、是否被污染）组成；模型写的 `reasoning` 与 `reason_for_user` 只进审计日志（清洗、截断）。否则一个被命令文本操纵了的模型可以借理由对 agent 说话。
- **任何失败都是 `on_failure`**（默认 ask，可设 deny，永远不是 allow）：超时、限流、5xx、4xx、认证失败、网络错误、无效输出、后端没实现、发送出口拒绝、预算之后才到的回答、内部异常。
- **出站目标**：只允许 https（本机回环地址除外）；不跟随任何重定向；只接受未压缩的回答，最多 256 KiB；一次审计的总预算是 `timeout_ms`，最多 6 秒，是整次尝试（名字解析、连接、TLS、响应头、响应体）的硬期限，逐字节滴发响应头的服务拖不长它；卡住的名字解析在后台线程里自己结束，审计不等它（同时最多 8 个，再多就直接按 `network` 失败；X1 审查 F5）；最多重试一次，只针对超时、限流、5xx、网络错误，且剩余预算足够时，限流时的 `Retry-After` 不是不超过 2 秒的纯秒数就不重试。错误信息不含请求体、回答体与密钥；密钥只从 `api_key_env` 指定的环境变量读，只放在请求头里。
- **守护进程的期限**：带 LLM 审计的审查期限是规则的 2 秒加预算再加 0.5 秒，从请求提交时算（排队的请求也有）；超时时 enforce 下按 `on_failure` 回答。

## 4. LLM 审计层做不到什么

- **不能识别"看起来和任务相符"的恶意动作**，如果规则也认不出来。规则层仍然是第一道、也是确定性的一道；模型只处理灰色地带，而它的判断质量 M3a 没有测过（M3b 的事）。
- **间接运行 boundkeep 的状态命令**（`mode`、`uninstall`、`init`、`serve`、`trust`、`taint`）：`deny-boundkeep-state-commands` 认得出 `boundkeep`、`boundkeep.exe`、`python -m boundkeep` 及其模块（`boundkeep.cli`、`boundkeep.__main__`，X1 复审 R-4）、`uv run` / `uvx` / `pipx run` 这些启动方式；更间接的写法认不出，是灰色：`python -c "from boundkeep.cli import main; …"`、`python -m runpy boundkeep …`、按路径运行 `cli.py`、`cmd /c`、`Start-Process`、`bash -c`。没有 LLM 时它们问用户；配置了 LLM 时由模型判断（命令文字在请求里）。`trust add` 与 `taint clear` 另有运行时的两道检查，`mode` 与 `uninstall` 没有。
- **任务意图本身可能被污染**：用户自己粘贴的文字不进任务意图（只留一个标记和长度），但用户亲手打的字如果是照着网页抄的，模型无从分辨。
- **缓存**：同一个问题（同样的动作、意图、污染位、后端、模型、提示词版本）10 分钟内（`cache_ttl_s`）直接用上次的模型结论，代码仍然重新裁决一次。缓存只在内存里。
- **同一用户的其他进程**能冒充守护进程、读写 `session.sqlite`、改环境变量里的密钥；这些都在规格 §3 的范围外。
