## 2. 发现

### R33-1（低，隐私，比修订 32 少换）：选项后面的值是一串路径时，整段按路径的边界

规则层把选项后面的整段值记成一个路径原文，哪怕它是一串路径：
- `-Wl,…` 记下的是 `-Wl` 后面剩下的整段（记录说是 `,-rpath,…`，只在后面没有别的时成立）；
- `-DCMAKE_PREFIX_PATH=…` 记成 `_PREFIX_PATH=…`。

修订 33 让这段值用路径的边界，主目录后面是 `,`、`;`、`:` 时不算结束。

整条链路，新代码和 `68ab7c7` 各跑一次：

| 写的 | 主目录 | `args`、`flags`：修订 33 | 修订 32 | `paths` | 送审吗 |
|---|---|---|---|---|---|
| Git Bash `gcc -Wl,-rpath,/c/Users/<名字>,-z,now a.c` | `C:\Users\<名字>` | 原样，带用户名 | `-Wl,-rpath,~,-z,now` | `<project>/,-rpath,/c/users/<名字>,-z,now` | 送 |
| PowerShell `gcc '-Wl,-rpath,C:\Users\<名字>,-z,now' a.c` | 同上 | 原样 | `~` | `<project>/,-rpath,c/users/<名字>,-z,now` | 送 |
| Git Bash `cmake '-DCMAKE_PREFIX_PATH=/c/Users/<名字>;/opt/b' .` | 同上 | `args` 原样 | `~;/opt/b` | `<project>/_prefix_path=/c/users/<名字>;/opt/b` | 送 |
| PowerShell `cmake '-DCMAKE_PREFIX_PATH=C:\Users\<名字>;C:\x' .` | 同上 | `args` 原样 | `~;C:\x` | `<project>/_prefix_path=c/users/<名字>;c/x` | 送 |
| PowerShell `gcc '-Wl,-rpath,\\server\share\<名字>,-z,now' a.c` | `\\server\share\<名字>` | 原样 | `~` | `<project>/,-rpath,/server/share/<名字>,-z,now` | 送 |
| Git Bash `gcc -Wl,-rpath,//server/share/<名字>,-z,now a.c` | 同上 | 原样 | `~` | 同上 | 送 |
| Git Bash `gcc -I/c/Users/<名字>:/opt/inc a.c`、`tar --directory=…:/x` | `C:\Users\<名字>` | 原样 | `~` | 其中一条带 U+F03A | 不送（路径里有格式字符，拒绝） |

- 这几条里，主目录就是这串路径中的一个：
  - gcc 在逗号处切开 `-Wl` 的值，链接器拿到的 `-rpath` 就是主目录（子代理用 `gcc -###` 看过）；
  - CMake 的列表用 `;` 分隔（CMake 的文档）。

  该写成 `~`。
- `command` 两版都换。
- 用户名不会因此多发出去，多出来的只是原来的大小写：
  - 会送审的几条，`paths` 本来就带着用户名（小写）；
  - 这是规则层的读法：它把 `-Wl,` 后面的整段、`-DCMAKE…` 的值读成项目下的一个相对路径；
  - 修订 32 的记录（`docs/reports/M3a-rev31-review-fixes.md`）第 6 节说过同一类（MSVC 的 `/I`、`/Fo`）。
- 但这和规格不一致：
  - 修订 32、33 都说列表照命令全文的规定换；
  - 修订 31 说过"不能因为加了边界就少换"。
- 记录和提交说明里有一句因此不准："UNC 主目录下的路径是网络访问，不送审，会送审的只有注释、字符串里的"。上面两条 UNC 的 `-Wl` 送审了，规则层没有把它读成 UNC 路径。
- `make --directory=<主目录>,x` 是一个叫 `<名字>,x` 的兄弟目录（make 不切逗号），修订 33 原样是对的。发送闸门分不出它和上面几条。
- **建议**（要使用者定）：
  - A. 路径的边界里，`,`、`;` 也算结束，斜杠写法的 `:` 也算（盘符写法本来就算）。选项后面的值和整个词是路径的，都这样。
    - 好处：`-Wl,-rpath,<主目录>,…`、CMake 的列表、修订 32 起就不换的 `java -cp /c/Users/<名字>:/x` 都会换。
    - 代价：名字里有 `,`、`;`、`:` 的兄弟目录（很少见）会多换成 `~,x`。宁可多换。
  - B. 不改代码，只改规格文字，写明这几种在 `args`、`flags` 里原样，用户名本来就在 `paths` 里。
  - 不论哪种，记录里那句"UNC 不送审"都照实改。

  建议 A。

### R33-2（低，隐私，比修订 32 少换，少见）：合选项形状的前一段不一定是选项

`_OPTION_PREFIX` 只看前一段的形状：`-`、`--` 或 `/`，一个字母，再跟字母、数字、`_`、`-`，可以带 `=` 或 `:`。合这个形状的，不一定是选项：

| 词（`args`） | 同一个动作的路径原文 | 主目录 | 修订 33 | 修订 32 | 怎么量的 |
|---|---|---|---|---|---|
| `echo /c/Users/<名字>/x > /Users/<名字>/x` 的 `/c/Users/<名字>/x` | `/Users/<名字>/x` | `C:\Users\<名字>` | 原样（前一段 `/c`） | `~/x` | 整条链路 |
| `echo /cygdrive/c/Users/<名字>/x > /c/Users/<名字>/x` 的第一个词 | `/c/Users/<名字>/x` | 同上 | `/cygdrive~/x` | `~/x` | 整条链路 |
| 同上，`/mnt/c/…` | 同上 | 同上 | `/mnt~/x` | `~/x` | 整条链路 |
| `/srv/home/<名字>/x` | `/home/<名字>/x` | `/home/<名字>` | `/srv~/x`（另一个路径） | 原样 | 直接调用 |
| `-C:\Users\<名字>\x` | `\Users\<名字>\x` | `C:\Users\<名字>` | 原样（前一段 `-C:`） | `-~\x` | 直接调用 |
| `/root/tmp/x` | `/tmp/x` | `/root` | 原样（前一段 `/root` 就是主目录） | `~/tmp/x` | 直接调用 |

- 要出现，得有一个词不是路径原文，却以同一个动作另一个路径的原文结尾。
  - 规则层读成路径的词自己就是原文，长的先试，会先按整个词换。
  - `echo` 的参数加重定向的目标就能凑出来。
  - 语料和 74 条探针里都没有这种词。
- 第一行的用户名，`command` 和 `paths` 里本来就有：另一个路径 `/Users/<名字>/x` 就带着它。
- 只在 `args` 里发出用户名的，要像第五行那样：路径原文 `\Users\<名字>\x` 被规则层读成主目录下的路径。这只用直接调用量过，没有找到能凑出它的真实命令。
- 规格修订 32 对斜杠写法只认 `-`、`--` 开头的选项（`/x/home/<名字>` 是另一个路径）。修订 33 的 `_OPTION_PREFIX` 不分写法，`/` 开头的也认。
- 记录说"选项那段也换"的变异存活是等价的，理由是选项那段里不会有主目录的写法。上表最后一行就有：主目录是 `/root` 时，这个变异给 `~/tmp/x`，新代码给 `/root/tmp/x`。不是等价的，提交说明里的这一句也不准。
- **建议**：只在切开的地方不落在主目录某种写法中间时才切。
  - 先按命令全文的边界在整个词里找主目录的写法。有一处跨过切开的地方，就不切，按命令全文的边界换整个词（管第五行）。
  - 前一段以 `/` 开头时，后面的路径原文不能以 `/` 开头，和修订 32 对斜杠写法的选项一致（管第一到四行和最后一行）。
  - 补测试，包括能抓到"选项那段也换"的。

### R33-3（低，多换，修订 33 新增）：UNC 带反斜杠的两种写法，用了盘符写法的左边界

`_home_pattern` 把"盘符或反斜杠开头"的写法放在一起，前面用 `_BEFORE_DRIVE`：除了选项，只要前一个字符不是字母、数字或下划线，就算名字的开头。
- 盘符写法前面不会是 `.`、`\`、`~`，这样没有问题。
- UNC 的 `\\server…` 前面紧挨着 `:`、`.`、`\`、`~` 时，却是另一个路径。修订 32 把 UNC 的写法当作斜杠写法，前面用 `_BEFORE_SLASH`，`.`、`\`、`/`、`~` 都不算开头。

| 写的（命令全文的注释，或路径词） | Win32 读成（`GetFullPathNameW`） | 修订 33 | 修订 32 |
|---|---|---|---|
| `C:\\server\share\<名字>\notes.txt` | `C:\server\share\<名字>\notes.txt`，C 盘上的目录 | `C:~\notes.txt` | 原样 |
| `.\\server\share\<名字>\notes.txt` | 当前目录下的相对路径 | `.~\notes.txt` | 原样 |
| `~\\server\share\<名字>\notes.txt` | 当前目录下 `~` 目录里的相对路径 | `~~\notes.txt` | 原样 |
| `x\\\server\share\<名字>\x` | 当前目录下的 `x\server\…` | `x\~\x` | 原样 |
| `\\\server\share\<名字>\notes.txt`（三个反斜杠） | 原样返回（服务器名为空） | `\~\notes.txt` | 原样 |
| 路径词里的转义写法 `\\\\server\\share\\<名字>\\x` | `\\\server\share\<名字>\x`（PowerShell 里不转义） | `~\\x` | 原样 |

- 整条链路量过一条：PowerShell 的 `python -c "print('C:\\server\share\testuser\x')"` 送审，`command` 和 `args` 里是 `C:~\x`。
- 规则层读成路径时，`paths` 是对的，两处说法不一致：PowerShell 的 `Get-Content C:\\server\share\John\notes.txt`，`paths` 是 `c:/server/share/john/notes.txt`，`args` 是 `C:~\notes.txt`。
- 后果只是多换：模型看到 `~`，实际不是主目录。用户名不会因此多发出去。
- 规格修订 33 说前两种"按盘符开头的写法处理"，写的只有右边界（`\`、单个尾随点、路径词里的 `:`），没写左边界也跟着变了。
- 写法很少见：UNC 写法前面要紧挨着另一个字符。
- 同一类、原来就有的：URL `http://server/share/<名字>/x` 里的 `//server/share/<名字>` 也换成 `~`，成了 `http:~/x`，修订 32 也这样。主机名在 `domains` 里，模型看不到的是 URL 的路径。`file://server/share/<名字>/x` 本来就是主目录，换得对。
- **建议**：
  - UNC 带反斜杠的写法单独用一个左边界：前一个字符不是字母、数字、下划线，也不是 `.`、`\`、`/`、`~`、`:`。也就是斜杠写法的那几个，再加 `:`。
  - 粘着选项的照旧。
  - 加测试。不改的话，至少写进规格"多换"的列表。

### R33-4（信息，文档）：UNC 主目录的另几种 Win32 写法不换，规格没写

| 写的 | Win32 读成 | 修订 33（命令全文 / 路径词） | 修订 32 |
|---|---|---|---|
| `\\?\UNC\server\share\<名字>\notes.txt`、`\\.\UNC\…` | 主目录（`GetFullPathNameW` 原样返回） | 不换 / 不换 | 不换 |
| `//?/UNC/server/share/<名字>/notes.txt` | 主目录（读成 `\\?\UNC\…`） | 不换 / 不换 | 不换 |
| 混用分隔符：`\\server\share/<名字>/…`、`//server/share\<名字>\…`、`/\server\…`、`\/server/…` | 主目录 | 不换 / 不换 | 不换 |
| `//server/share/<名字>\notes.txt` | 主目录 | 不换 / `~\notes.txt` | 不换 / 不换 |
| `//server/share/<名字>./notes.txt` | 主目录 | 不换 / 不换 | 不换 |

- 真去访问这些路径，规则层都按网络访问问，不送审（`\\?\UNC\…` 量过，`paths` 是 `~/notes.txt`）。
- 会送审的只有注释、字符串里的。整条链路量过：PowerShell 的 `python -c "print('\\?\UNC\server\share\testuser\x')"` 送审，`command`、`args` 带着用户名。
- 盘符主目录的对应写法：`\\?\C:\Users\<名字>` 换（修订 32 的复审量过）；混用分隔符的 `C:\Users/<名字>` 不换，规格修订 32 写明了。UNC 的这几种，规格修订 33 都没写。
- 正斜杠写法后面跟 `\`：规格只说 Git Bash 里 `\` 是转义。PowerShell 里这就是主目录，修订 31 换它。和规格修订 32 写明的 Git Bash `'/c/Users/<名字>\x'` 是同一类代价。
- **建议**：写进规格的"不换的写法"。`\\?\UNC\` 这个前缀要不要认，可以和 R33-3 一起定：它和 `\\?\C:\…` 对称，加一种写法就够。

## 4. 建议的顺序

1. R33-1、R33-2 一起改，都在 `_word` 和路径的边界：先改规格（新开修订 34），再改代码。R33-1 要使用者先在 A、B 里定一个。判决和送不送审不变。
2. R33-3 改代码：UNC 带反斜杠写法的左边界。顺带定 R33-4 里的 `\\?\UNC\` 要不要认。
3. R33-4 只改规格文字。修订 33 记录里三句说法照实改：
   - UNC 主目录下的路径不送审（R33-1）；
   - `-Wl` 的路径原文（R33-1）；
   - "选项那段也换"的变异是等价的（R33-2）。
